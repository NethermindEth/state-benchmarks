# End-of-Grant Report — State Bloating & EL Benchmarking

**Project:** State Benchmarks — Ethereum execution-layer performance at 10× mainnet state
**Grant lead:** Marcin Sobczak · **Team:** Daniil Ankushin, Dmytro Biloshytskyi · **EF contact:** Marius van der Wijden
**Repository:** [NethermindEth/state-benchmarks](https://github.com/NethermindEth/state-benchmarks) · **Results site:** [nethermindeth.github.io/state-benchmarks](https://nethermindeth.github.io/state-benchmarks)
**Status:** ✅ Concluded — all milestones met (confirmed with EF on 2026-07-22).

---

## 1. Executive summary

We bloated a **real mainnet snapshot to 10.03× (2.22 TB)** with mainnet-faithful composition and benchmarked two execution clients (Nethermind, Geth) end-to-end — generation, snap-sync, execution, and witness sizing — reproducing every milestone bit-for-bit against the canonical state root.

**Headline:** *a 10× state is not a 10× cost.* What strains clients is **gas throughput and a few giant contracts**, not the size of the state — trie depth and proof size stay almost flat (log-bounded). All the tooling, data, and client fixes are open and reusable for future forks.

---

## 2. Outcomes

1. **Clients hold at 10× — no collapse.** Both clients executed, served RPC reads, and snap-synced the full 10× state. No performance cliff between 1× and 10×; the strain that appeared tracked **gas throughput**, not state size.
2. **Trie depth grows as log₁₆(N) — witnesses stay tiny.** Account-trie depth follows `log₁₆(N)` (R² = 0.99998); the whole 1×→10× climb adds under 1 level (7.61 → 8.45). A single account proof grows **+11%** over 1×→10× (**~+21%** extrapolated to 100×). This is the real-state MPT baseline for any binary-tree migration (EIP-7864).
3. **Snap sync is linear — but one giant trie is the wall.** ~100 GB/h (Nethermind) / ~47 GB/h (Geth) from a single peer; a full 10× sync takes 27–46 h, bit-exact. One giant-contract storage trie took **~9 h — a third of the entire 10× sync** — as a non-parallelisable sequential chain (Amdahl).
4. **Every state is reproducible and verifiable.** Each milestone is generated through the real Engine-API state-transition path, replayable by any client and verifiable against the state root. The tooling is a ready state-scale regression suite for devnets and CI.

## 3. Recommendations for core developers

| Track | Recommendation |
|---|---|
| Harden L1 · Resilience | **Make giant-contract snap sync parallelisable** (primary ask). A complementary lever is pricing — building such a trie is gas-metered (~20 k gas/slot), but that one-time cost doesn't reflect the permanent per-node sync/storage burden. |
| Harden L1 · Interop | **Fix p2p body sizing before large blocks** — at 8-Ggas blocks, bodies reach 26–47 MB and overflow the 16 MB devp2p / 24-bit RLPx frame (fixed & merged in Nethermind #12059). |
| Scale · Glamsterdam | **Reprice on state accesses, not proof bytes** — the witness is log-flat in size, so a block's witness ≈ (state accesses) × (roughly constant per-access cost). |
| Harden L1 | **Add snap-serving peers** — the box sat ~80% idle at 5×; the ceiling is single-peer request concurrency, not hardware. |

## 5. Reproducibility & limitations

- **Reproducible:** every milestone is verifiable bit-for-bit against its canonical state root; the payload stream + tooling reproduces any state on any client.
- **Client coverage:** Nethermind and Geth fully benchmarked; Besu, Erigon, and Reth partially covered.
- **Sync times** are single-peer lab numbers, not real-world (real syncs pull from many peers).
- **Some downstream numbers are projections** (the binary-tree proving factor, specific gas constants) and should be verified before external citation.
